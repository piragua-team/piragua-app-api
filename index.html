API institucional Piragua: rutas que consume la app móvil

Versión del contrato 1.10.6 · OpenAPI 3.0.3 · 31 operaciones · 45 esquemas

Contrato del API institucional visto desde la app móvil Piragua. No describe el API completo: solo las rutas que el código de la app llama, con el método, los parámetros y la forma de respuesta que la app lee de verdad. La versión del contrato es la de la app que describe, la 1.10.6, con el mismo nombre en las dos tiendas: publicada en Google Play el 2026-10-15 y en revisión en la App Store. Lo que cambia respecto de la 1.10.5.1, que en iOS lleva el número 1.10.5 (build 9) porque Apple solo admite tres números en la versión, va marcado «desde la 1.10.6». Cada operación lleva dos extensiones: x-estado, que vale en uso cuando el código del árbol la llama hoy y propuesto cuando es un contrato que la app necesita y el Sistema todavía tiene que confirmar; y x-origen, la lista de ficheros que la llaman. Donde la forma de una respuesta no se conoce, el esquema es type: object con la descripción «forma no documentada»: nada de lo que aquí figura se ha inventado. La prueba __tests__/openapi-app.test.js cruza las rutas de slices/ contra este fichero. Cada operación trae un ejemplo de petición y de respuesta con los campos que la app lee; los datos de los ejemplos son ficticios (__tests__/openapi-ejemplos.test.js comprueba que ninguna operación se quede sin ejemplo y que cada ejemplo contenga las claves obligatorias de su esquema). Las reglas de los formularios de estaciones (campos obligatorios, rango de la muestra de lluvia, fecha no posterior a hoy y versión de formulario) están en docs/FORMULARIOS.md, y __tests__/formularios-doc.test.js las ata a validarLluvia y a slices/constants.js. El manual de referencia en HTML, docs/api/index.html, se genera desde este contrato con node bin/generar-manual-api.mjs; __tests__/manual-api.test.js falla si el contrato cambia y el manual no se regenera. Versión del API contra la que se verificó: API 1.3.8 (también en x-version-api), la de la especificación oficial del Programa, publicada en https://piragua.corantioquia.gov.co/developers/api.yaml; los códigos de respuesta, la ruta /documentos y la forma de /multimedias salen de esa especificación. El cotejo operación por operación, con las diferencias y a quién le toca cada una, está en docs/CONTRATO-API.md.

Página generada por bin/generar-manual-api.mjs a partir de docs/openapi-app.json. No se edita a mano: se cambia el contrato y se regenera; __tests__/manual-api.test.js falla si el manual guardado no corresponde al contrato.

Autenticación

bearer · oauth2

Token de acceso OAuth2 obtenido con el flujo de contraseña sobre POST /login, que recibe client_id, client_secret, grant_type (password), username (nombre de usuario o correo) y password en un cuerpo JSON (no en formulario) y devuelve el token dentro de oauth2.access_token. slices/apiClient.js añade Authorization: Bearer <token> a toda petición relativa mientras haya sesión y cierra la sesión local ante el primer 401 de cada ráfaga. Nunca se envía a URL absolutas de otros hosts.

flujo password · tokenUrl: https://geopiragua.corantioquia.gov.co/api/v1/login · sin alcances

La app envía en el cuerpo JSON las credenciales del cliente OAuth2, la concesión grant_type con el valor password y las de la persona: en username, su nombre de usuario o su correo, y en password, su contraseña. Desde la 1.10.5.1 la pantalla de ingreso acepta el usuario o el correo (antes exigía un correo) y el cuerpo declara grant_type, como hace el portal web ante el mismo servicio (docs/CONTRATO-API.md, A-06). La respuesta es el usuario completo con un bloque oauth2 que trae el access_token; la app guarda en el teléfono solo los campos de ESQUEMA_DE_SESION (context/sessionStorage.js), y el refresh_token lo aparta de la respuesta y lo guarda cifrado en el almacén seguro del sistema (slices/tokenDeRenovacion.js) para renovar el token de acceso con /oauth2/token/. screens/auth/Signup.js inicia sesión por la misma ruta y con el mismo servicio (iniciarSesion, slices/servicios/usuarios.js) justo después de registrar la cuenta. Sin Bearer: es la llamada que lo obtiene. El servicio distingue mayúsculas en username (medido el 2026-10-14: el usuario de prueba tal cual entra y en mayúsculas recibe 400 «Credencial invalida»). Desde la 1.10.6, si el servicio rechaza las credenciales (invalid_grant o Credencial invalida) y lo escrito no es lo que se envió, porque era un correo con mayúsculas, la app repite el ingreso una sola vez con lo escrito tal cual; ningún otro fallo lo repite (docs/CONTRATO-API.md, S-14 y A-10).

4XX respuesta compartida ErrorDeValidacion

Error de validación de un formulario: además de las claves de Error, el cuerpo puede traer mensajes por campo ({ campo: 'mensaje' } o { campo: ['mensaje'] }), que la app muestra para que la persona sepa qué corregir: el texto de cada campo que el formulario pinta va bajo ese campo; detail, non_field_errors y las claves que el formulario no muestra van en el recuadro de avisos del formulario, sin el nombre de la clave. Respuestas compartidas

NoAutorizado

Sin sesión válida. En rutas relativas del API institucional, slices/apiClient.js cierra la sesión local y la app vuelve a la pantalla de ingreso.

application/json

Esquema: Error

Ejemplo

{
  "detail": "Las credenciales de autenticación no se proveyeron."
}

ErrorDeCliente

Error del cliente distinto de 401. La app muestra detail, error, errors o non_field_errors cuando vienen; si el cuerpo no es JSON, muestra un mensaje propio. Desde la 1.10.5, donde la app muestra ese texto, un 429 (límite de peticiones del API, {"detail": "Too Many Requests"}) lleva en su lugar su propio aviso en español (slices/errores.js).

application/json

Esquema: Error

Ejemplo

{
  "detail": "No encontrado."
}

ErrorDeValidacion

Error de validación de un formulario: además de las claves de Error, el cuerpo puede traer mensajes por campo ({ campo: 'mensaje' } o { campo: ['mensaje'] }), que la app muestra para que la persona sepa qué corregir: el texto de cada campo que el formulario pinta va bajo ese campo; detail, non_field_errors y las claves que el formulario no muestra van en el recuadro de avisos del formulario, sin el nombre de la clave. Si el cuerpo no trae ningún texto legible, la app muestra su aviso genérico. Un 429 (límite de peticiones del API) no se reparte por campos: desde la 1.10.5, donde la app lo muestra, lo hace con su propio aviso en español y no con el texto del servidor.

application/json

Ejemplo

  ],
  "user": {

  }
